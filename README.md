# agentprof: measuring what LLM agent sessions hold on serverless and agent runtimes

Artifact for *Paying for Isolation: Characterising LLM Agent Turns on Serverless
and Agent Runtimes* (submitted to ICPE 2027, Industry Track).

An LLM agent step waits seconds on a model and computes for milliseconds.
Platforms that dedicate an environment to each session hold that environment
through the wait. This repository holds everything needed to reproduce the
paper's numbers: the framework-CPU benchmark (with the model faked at the
network socket), the on-platform deployment for AWS Lambda and Amazon Bedrock
AgentCore Runtime, 3,549 steps of deployed agents, the capacity analysis, the
direct concurrency measurement, and the hosting-policy simulation.

Everything runs offline except the two optional cloud runs, and nothing calls a
model: the benchmark fakes the socket, so no tokens are spent anywhere.

## Set-up

Python 3.12 or later. The tracer and tests need nothing beyond the standard
library; the benchmarks need the pinned frameworks.

```bash
python3 -m venv .venv
.venv/bin/pip install -r cloud/requirements.txt matplotlib numpy simpy pypdf
python3 tests/test_agentprof.py          # 19 tests, about a second
```

`cloud/requirements.txt` pins the exact library versions measured in the paper
(LangGraph 0.6.11, langchain-aws 0.2.35, Strands 1.55.0, boto3 1.42.97).

## Reproducing the paper

| Paper item | Command | Time |
|---|---|---|
| Table 2, Figure 1 (local machine rows) | `.venv/bin/python scripts/measure_framework_cpu.py --steps 40 --replicates 40 --out data/framework_cpu_raw_x86.json` then `scripts/measure_strands_cpu.py --replicates 120` | ~15 min |
| Table 2 (AgentCore rows), Table 3 (Lambda) | `cloud/aws.py` (see `cloud/README.md`; needs an AWS account, costs under $2) | ~1 h |
| Section 4.4, Section 5, scenario numbers, Figure 1 | `.venv/bin/python scripts/sensitivity.py` | seconds |
| Section 5, direct measurement | `.venv/bin/python scripts/validate_capacity.py` | ~40 min, uses 5 cores |
| Figure 2 | `.venv/bin/python scripts/fig_capacity_alt.py` | seconds |
| Figure 3, Section 7 | `.venv/bin/python scripts/simulate_remedy.py` | ~4 min |

The analysis scripts read the shipped data, so Sections 4–7 reproduce without
re-running any benchmark. Re-running a benchmark overwrites the corresponding
file in `data/`; constants will differ on your hardware, and the paper argues
that only the linear form transfers.

## The deployed data

`data/deployed_turns.csv` was collected in September 2026 for a separate study
of the same agents. Each row is one warm step: configuration, task, trial,
turn index, input and output tokens, model time, overhead outside the model
client, and total server time. Model time was measured around the model-client
call and therefore includes the client's own serialisation; the paper's
Section 3.3 explains why that matters and how the deployed CPU per step is
bracketed rather than measured. The deployed study's own harness is not part
of this artifact.

## Measurement caveats

Written into the paper's threats section; repeated here so a replicator meets
them first.

- CPU is per-thread for LangGraph (its tool node uses a thread pool, tracked
  explicitly) and process-wide over hook windows for Strands (its model call
  spans two threads). Do not mix the two clocks.
- A step run after a real wait on the model costs about twice the CPU of the
  same step run back to back (`scripts/validate_capacity.py`). Benchmarks that
  loop without waiting understate CPU by that factor.
- Both AgentCore and Lambda placed our runs on several processor generations.
  Record the host (`environment` in each result file) before comparing
  constants.
- The simulation's memory figures rest on an illustrative footprint (0.5 GB per
  process plus 10 MB per session); its environment counts do not.
